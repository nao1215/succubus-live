## Pathfinder（一次資料）

- Mike Jones の要約「What really happened on Mars?」1997-12-07 付け。RTSS での David Wilner（Wind River の CTO）の基調講演の要約。着陸は 1997-07-04。情報バス、高優先度のバス管理、低優先度の気象、中優先度の通信。ウォッチドッグがリセットしたという書き方。C インタプリタが残っていて、大域変数を FALSE→TRUE にする短い C のプログラムを送ったという書き方（ほかに同じ危険のある二つも）。打ち上げ前の試験で一、二度リセットがあり、ハードの気まぐれとされた。教訓四つ。CMU の Sha・Lehoczky・Rajkumar が会場にいて拍手された。論文は IEEE Trans. Computers vol.39、1990年9月。（読んだ）
  → https://www.cs.cornell.edu/courses/cs614/1999sp/papers/pathfinder.html
- Glenn Reeves の返信 1997-12-15。署名「Mars Pathfinder Flight Software Cognizant Engineer」。「たぶん400人から転送された」。Mike には会ったことがなく、シンポジウムにも行っていない。（読んだ）
  - CPU は一つで VME バスに無線・カメラ・1553 のカード。vxWorks は Wind River が RS6000 に移植。
  - 1553 のハードは Cassini から引き継ぎ、8 Hz で回す作法が付いてきた。
  - bc_sched は tExec を除いて最も高く、bc_dist は三番目（間は突入・着陸の係）。
  - ほとんどの係は二重バッファの共有メモリ。ASI/MET だけ pipe() と select()。
  - ASI/MET が select() → selNodeAdd() で mutex を返す途中で割り込まれ、bc_dist の pipeWrite() が同じ mutex で止まり、bc_sched が bc_dist の未完了を見つけてハードな締め切りの違反として計算機をリセット。「ウォッチドッグ」という言葉は使っていない。
  - リセットで RAM の収集済みデータは失われない（電源が落ちない限り）。その日の残りは次の日。
  - トレースは David Cummings が作り、Wind River の Lisa Stanley が pipe・msgQ・割り込み・select・tExec を計装。デバッグ機能は設計として飛行ソフトに残してあったが、トレースを飛行中に下ろすことはできなかった。
  - 「In less that 18 hours we were able to cause the problem to occur.」
  - 打ち上げ前の試験で起きていたが再現できなかった。試験は「best case」の高データ量だけ。「better than we could have ever imagined」の場合は予想も試験もしなかった。突入・着陸を優先。「We had our priorities right.」
  - 直し方：セマフォの作成フラグを変えて継承を有効に。Wind River が selectLib() に大域の設定変数を出し、以後作られる select のセマフォ全部に効く。性能の影響は小さい、「so long as there was always only one task waiting for any particular file descriptor」なら select の振る舞いは変わらない。地上で十分に試験してから送った。
  - 「No, we did not use the vxWorks shell to change the software (although the shell is usable on the spacecraft).」パッチは地上と機上の版の差分を送り、機上の専用ソフトが確かめて当てる。シェルと標準出力は任務の間ずっと役に立った。
  - 「There was no conscious decision to not have the priority inheritance option enabled. We just missed it.」JPL に誤りがあったかに「Yes, probably.」
  - 「test what you fly and fly what you test」「A good lesson when you fly COTS stuff - make sure you know how it works.」
  - 放射線による誤りから立ち直るように設計。大気中で複数回リセットしても大丈夫なように。
  → https://www.cs.unc.edu/~anderson/teach/comp790/papers/mars_pathfinder_long_version.html

## 継承と天井

- Sha, Rajkumar, Lehoczky「Priority Inheritance Protocols: An Approach to Real-Time Synchronization」IEEE Trans. Computers 39(9), 1990。基本の継承と天井の方式を並べた論文。（Jones の要約で書誌を確認。中身は一般に知られた内容で、論文本文は読んでいない）
- Victor Yodaiken「Against Priority Inheritance」FSMLabs の技術報告、2002年7月（2004年9月に改訂版）。継承は信頼できる実時間設計と相性が悪い、実装は不完全か驚くほど複雑で侵襲的、元の論文の「正しいと証明した」アルゴリズムは間違い、代わりに天井（欠点と解析の難しさも認める）。（検索）
  → https://www.yodaiken.com/papers/inherit.pdf
- Doug Locke（TimeSys）の反論、2002年。技術的な指摘は概ね正しいが結論はひどく誤り、継承は広く使われる重要な道具の一つ。（検索）
  → https://www.math.unipd.it/~tullio/SCD/2007/Materiale/Locke.pdf

## 今の OS

- FUTEX_LOCK_PI は Linux 2.6.18 から。rt-mutex で、-rt の木で育って pthread の mutex のために整えられた。継承は入れ子の鍵の連鎖をたどり、デッドロックを検出する。（検索）
  → https://man7.org/linux/man-pages/man2/FUTEX_LOCK_PI.2const.html
  → https://docs.kernel.org/locking/rt-mutex.html
- pthread の mutex の protocol の既定は PTHREAD_PRIO_NONE。継承は PTHREAD_PRIO_INHERIT、天井は PTHREAD_PRIO_PROTECT。（POSIX の規定。既知の内容）
  → https://pubs.opengroup.org/onlinepubs/9699919799/functions/pthread_mutexattr_getprotocol.html
- Windows の AutoBoost：鍵の持ち主に優先度の床を付け、待っている人の最高の優先度まで上げて、鍵を離すまで下げない。（読んだ）
  → https://learn.microsoft.com/en-us/windows/win32/procthread/priority-inversion
- Go の sync.Mutex の飢餓モード（Go 1.9 から、待ち手が1ミリ秒以上待たされると切り替わり、鍵を並んでいる人に直接渡す）。（ソースのコメントで知られる内容）
  → https://cs.opensource.google/go/go/+/refs/tags/go1.9:src/sync/mutex.go
- PREEMPT_RT は 2024年9月に本流に入り、6.12 が最初の版。Thomas Gleixner がプルリクエストを渡した。最後まで printk が引っかかっていた。（検索）
  → https://en.wikipedia.org/wiki/PREEMPT_RT
  → https://heise.de/-10061458

## Spirit（2004年）
